# 迁移、切换与回退检查单

当前是部署工具和本地预演阶段。本文件不表示服务器已恢复业务，也不表示备案、HTTPS或国内手机验收通过。旧站继续保留；任何时刻最多只有一个环境可以接受业务写入。

## 服务器私下预演

1. 使用最终复核后的版本包，保存包的本机SHA-256、源码提交号和测试报告。旧的 `task5-local-04` 包包含修复前的文件接口，只作历史证据。
2. 按本目录README，通过已核验主机身份的加密通道传输；root先复制至受保护staging目录，再以本机可信摘要核验、解包、安装。安装默认不启动worker/maintenance，不改防火墙。
3. 在目标创建独立staging数据库和新的受限LOGIN角色，开启PG严格TLS和loopback监听。先恢复已验证的备份，逐表核对规范摘要，再应用新增迁移；记录预期新增的delivery/control/admission表及单例行。不得在核对源快照之前应用迁移而混淆表摘要。
4. 原图按原UUID路径导入私有目录，逐个核对原字节SHA-256、大小、MIME和数据库关联；保留账号身份、密码哈希、评分标准、任务、结果、教师修订及持久幂等数据。不得重建账号或消费恢复的作业。
5. 用独立空数据库完成合成HTTP和fake provider预演。恢复的业务库保持worker及maintenance关闭。预演应覆盖登录、任务、上传、读取、批改、修订、重登恢复、教师隔离、停止与重启、权限和不含秘密的日志。
6. 对目标执行完整数据库和磁盘备份，并在独立数据库验证恢复。只有备份完整、摘要一致且有恢复证据，才可进入切换步骤。

## 冻结源站

以下命令从受控运维环境运行。管理员连接串和CA只从私密文件加载到进程环境；不放入命令参数、TAT记录或聊天。`migrationControl.ts`需要数据库管理员权限，普通运行角色没有冻结或解冻权限。

1. 在源站应用新增SQL迁移、部署已复核的兼容版本，并显式启用 `PILOT_MIGRATION_GATE_ENABLED=1`。确认API认证/管理员/GET隐式写入、队列回调、维护、签名及异步存储操作都经过同一冻结门。连接必须支持session advisory lock，不能使用transaction pooler。
2. 执行 `platform-api/node_modules/.bin/tsx platform-api/scripts/migrationControl.ts freeze`。它先拒绝新准入，再报告排空状态；一次命令不会等待两小时。
3. 保存每次状态和时间。`waiting_operations` 等待真实异步效果结束；`blocked_uncertain_operations` 或 `blocked_unknown_results` 必须调查，不能删除准入记录、清空provider gate或重发未知作业来强行通过。
4. 从首次确认排空开始，至少等待7920秒：7200秒旧上传签名窗口、120秒签名/时钟余量、600秒在途余量。`status`只读查询；等待结束不等于远端上传已经结束。
5. 实际观察源Storage上传已停止、无在途PUT，再执行 `freeze --confirm-source-uploads-idle`。只有返回 `state: ready`、无未决准入/执行/未知结果，才能制作最终切换备份。该确认不能按时间猜测。
6. 源API、worker和维护继续冻结。重新运行源站只读完整备份，要求表和对象清单稳定、缺图和摘要不符均为0，并验证独立恢复；此前在线快照不能替代这一份最终备份。

## 切换

前置证据必须齐备：备案通过、域名解析及HTTPS证书正确、最终冻结备份已恢复并核对、独立合成预演和目标恢复演练通过、回退备份在服务器之外保留。

1. 使用最终备份建立新的目标业务库，逐表逐图核对并应用目标迁移。复制来的冻结状态继续保留，worker和maintenance仍关闭。
2. 验证目标运行身份、私有磁盘权限、Nginx配置、HTTPS、可信代理、磁盘余量及环境配置。不能以API进程启动或登录成功代替完整就绪。
3. 先完成下方“冻结期间的队列衔接”的正向步骤并保留报告。确认源站仍冻结后，显式解冻目标；目标若报告未知或未决状态，停止并调查。开启目标worker/maintenance后核对就绪检查。迁移本身不改变全站模型并发1。
4. 解析和入口切换后，旧站继续冻结，避免旧标签页或缓存DNS写入第二个环境。源代码、数据库和图片保留，不立即销毁。
5. 真实模型验证只使用另行明确范围的一次性合成材料，不使用迁移来的学生作文。由用户分别使用国内Wi-Fi及手机流量、关闭VPN完成登录、上传/拍照、批改、保存、刷新与重登恢复；代理无法代替该网络验收。

## 回退

**目标尚未接受新写入：**停止目标新准入，确认无执行/在途上传，保留诊断证据。核实目标没有新增或变更业务数据后，才可恢复旧入口并显式解冻源站。

**目标已经接受新写入：**不能只改DNS回旧快照。

1. 冻结目标并排空所有实际效果；遇到未知执行或遗留准入即停止调查。保持两端冻结，不让旧站提前写入。
2. 制作目标PG和私有磁盘完整备份，保留规范表摘要、全部原图及关联、角色权限和迁移状态，并验证独立恢复。
3. 在独立恢复环境准备反向导入：恢复全部业务表和持久幂等状态；按原UUID路径把新增原图写回原私有Supabase桶，已有对象必须核验相同摘要，不能盲目覆盖。先保留源站当前备份，不在唯一源副本上直接试错。
4. 保留数据库任务/执行/provider gate作为幂等依据。PG的delivery记录不能当作Vercel的实际投递；执行下方显式反向队列衔接，才能由恢复逻辑按原generation为确实可投递的queued任务重新投递，未知任务不得重投。验证重复消费新增调用为0。
5. 比较反向恢复的账号、任务、评分标准、结果、教师修订、会话策略、全部图片及关联，完成合成闭环和权限检查。只有反向恢复验证通过、目标仍冻结，才允许切回并解冻源站。

反向导入和实际回退尚未在云端执行；在这一演练完成前，不把“保留旧站”称为已经具备无损的新写入回退能力。

## 冻结期间的队列衔接（解冻前必做）

Vercel 的实际消息不在数据库备份内。`outbox.sent_at` 和 `maintenance_jobs.sent_at` 只能证明旧后端发过消息，不能证明目标已有投递；普通恢复会等到24小时才重新发送。不能用启动worker替代衔接。

两个运维命令均已编译进版本包：从版本根运行 `node platform-api/scripts/migrationControl.js ...` 和 `node platform-api/scripts/queueHandoff.js ...`，不依赖服务器安装tsx或开发依赖。管理员连接串与PEM CA从受限私密文件载入 `DATABASE_ADMIN_URL` / `DATABASE_CA_CERT`，不得放在命令参数、聊天、日志或TAT命令里。

正向切换：完成最终冻结快照及逐表摘要校验后，目标仍保持冻结、worker/maintenance关闭。在目标服务器运行 `node platform-api/scripts/queueHandoff.js to-postgres --expected-database writewise_target`（替换为实际小写数据库名）。命令仅接受字面地址127.0.0.1及 `writewise_` 前缀数据库、显式CA，连接后再核对实际数据库名。它在同一连接持有管理员锁及排空锁，要求全站无准入、运行中/准备中/调用中/未知执行及占用provider gate；不满足则零修改失败。只对活跃教师的未删除任务且状态queued的作业，以原 `job_id:generation` 和精确 `outbox.available_at` 建立PG投递；queued维护任务按原身份和created_at建立投递（全局任务或活跃教师）。重复执行不会修改已存在投递，也不会重新打开完成投递。只输出新增数量，始终不解冻、不调用模型、不消费作业。保留衔接报告后才继续“切换”第3步。

反向回退：先完成目标冻结、源站保护备份、反向数据/图片导入和验证，保持两端冻结。仅在明确决定回退且恢复后的源库已核验时，从受控运维环境运行 `node platform-api/scripts/queueHandoff.js to-vercel --expected-database postgres`。该模式硬性限定已核实的源项目 `wudbhdyqgnbnuorebhnu`、`aws-0-ap-southeast-1.pooler.supabase.com:5432` session端点及 `postgres.<项目ID>` 管理员用户名，不接受transaction端口。它通过相同冻结/排空检查，只清除合格queued作业及维护任务的 `sent_at`，保留generation、available_at和所有执行/结果/PG投递；后续显式解冻才由原恢复逻辑重投至Vercel。不能在仍作为唯一生产源的库上“试运行”此模式。确认两端摘要和队列衔接报告后再继续回退第5步。
