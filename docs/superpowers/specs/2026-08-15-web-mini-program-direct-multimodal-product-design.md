# 网站与微信小程序统一多模态批改产品设计

## 状态

- 日期：2026-08-15
- 状态：用户已批准
- 方案：在现有图片直传多模态链路上渐进收敛
- 产品形态：教师端网站 + 教师端微信小程序

## 决策摘要

文阶最终只提供网站和微信小程序，不开发独立桌面软件。网站与小程序功能完整对等、共享同一套账号、任务、作文图片、批改结果和教师修改记录；两端只根据屏幕与输入方式调整交互，不建设两套业务系统，也不把小程序做成网站的精简版。

学生作文不再经过独立 OCR 服务或批改前转写确认。图片按页序直接交给多模态模型，由一次请求完成正文理解、学生原文生成、评分和反馈。批改后仍保留“学生原文”文本层，用于原句定位、证据校验、教师抽查和修订后重批，但产品和代码主模型中不再把它称为 OCR。

拼写采用有利于学生的高确定性策略：可合理理解为正确单词的字形歧义默认正确；只有字母清楚、错误明确且正确写法唯一时才报告拼写错误。会改变语义或评分的重要字迹歧义默认判为“卷面与可读性错误”，但不得伪装成具体拼写、语法或逻辑错误。产品反馈优先语法、逻辑、任务完成度和表达问题。

## 目标

1. 将现有新任务的图片直传 Kimi 多模态批改链路确立为唯一主流程。
2. 删除独立 OCR Gateway、OCR 状态、OCR 异常队列、OCR 置信度和兼容分支。
3. 保留批改后学生原文及证据定位能力，并支持教师局部修订后显式重批。
4. 让真实 AI 返回结构化语法问题和逻辑问题，修复当前真实结果中逻辑问题未贯通的缺口。
5. 网站和微信小程序完整覆盖教师工作流并实时同步。
6. 尽量保留现有网站页面布局、路由结构、侧边导航、卡片和 Tab，不进行与本设计无关的视觉重构。

## 非目标

- 不开发 Windows、macOS 或其他独立桌面客户端。
- 首版不建设学生端或家长端；后续可以复用同一后端扩展。
- 不追随竞品扩展课堂抽奖、点名、备课材料等外围教师工具。
- 不在本轮重做现有网站视觉系统。
- 不恢复伪精确的词级或全文 OCR 百分比置信度。
- 不允许静默自动重试产生重复模型费用。

## 总体架构

系统只保留一条业务主链路：

`网站 / 微信小程序 → 共享业务后端 → 对象存储 → 批改队列 → 多模态批改 Gateway → 结构化结果`

共享业务后端负责：

- 教师账号、班级、学生、任务和评分标准；
- 作文、图片、页序、分组和上传状态；
- 批改任务、幂等请求、状态流转和错误恢复；
- 学生原文、评分、问题、优化稿、教师调整和版本历史；
- 班级讲评、导出任务和跨端同步。

图片二进制存放在对象存储中，数据库只保存受控元数据和对象引用。多模态 Gateway 不持久化原始 Base64，不在日志中记录作文正文、学生身份、图片内容或 Provider 原始响应。

网站与小程序复用同一套 API、类型契约、状态机、评分规则和权限边界。客户端可以采用不同的界面实现，但不得复制或分叉核心批改规则。

## 双端完整功能

网站和微信小程序都提供以下一级能力：

1. 工作台：待批改、批改中、待确认、失败和最近完成任务。
2. 批改任务：创建任务、上传题目材料、确认评分标准和管理任务。
3. 作文上传：拍照、相册或文件导入、页序调整、多页合并、批量分组和提交。
4. 批改队列：查看状态、启动批改、失败重试、转人工和批量选择。
5. 单篇批改：原图、学生原文、分项评分、问题定位、全文优化和教师反馈。
6. 班级讲评：分数分布、高频语法、典型逻辑问题、教师精选和改写练习。
7. 班级管理：班级、学生名单、历史任务和作文档案。
8. 导出中心：生成、预览、下载和分享单篇或批量 Word/PDF。
9. 批改设置：评分严格度、反馈详略、评级方式、批改内容和导出样式。

网站继续利用大屏完成批量处理、左右对照和密集审核。小程序将同一能力拆成移动端步骤：原卷全屏查看、双指缩放、触控批注、底部操作栏、分层结果 Tab 和多选批量面板。复杂功能不得因移动端而删除。导出文件由云端生成，小程序负责预览、下载和转发。

## 现有网站布局约束

网站保留当前主要路由和页面职责：

- 任务列表 / 工作台；
- 创建任务；
- 上传整理；
- 批改进度；
- 待确认队列；
- 单篇结果；
- 班级总览。

具体调整限制如下：

- 保留现有侧边导航、任务流程导航、卡片和主要按钮位置。
- 上传整理页继续使用现有图片分组、排序、合并和拆分结构。
- 批改进度页保留现有状态概览、筛选 Tab 和作文行。
- 原“异常复核”页复用为“待确认队列”，删除 OCR 文本编辑器和 OCR 异常原因，改为展示结果级安全校验问题及进入单篇详情的操作。
- 单篇结果继续保留原文区域以及“评分诊断、问题批改、全文优化、教师反馈”四个 Tab。
- “OCR 文本、编辑 OCR、OCR 置信度”等文案统一改为“学生原文、修订学生原文、识图说明”。
- 原卷视图和教师标注能力在现有页面级工作区内完善，不另起一套详情页。

## 状态模型

统一作文状态为：

`uploaded → queued → grading → review_ready → completed`

补充终止或恢复状态：

- `failed`：上传、服务调用或结果安全校验失败，可显式重试；
- `manual`：教师决定转人工处理。

删除 `pending_ocr`、`ocr_running`、`low_ocr_confidence` 等 OCR 专属状态和原因。`review_ready` 表示 AI 已返回可展示结果，等待教师确认；安全校验发现引用、分数或结构异常时仍停留在该状态并展示具体原因，不建立第二套 OCR 复核状态机。

首次批改使用有序图片。教师修订学生原文后，旧结果保留为历史版本但当前结果失效；再次批改只发送教师确认文本和任务包，不重复识图。每次保存、确认、重批和导出都带版本号，旧版本写入必须被拒绝并提示刷新，禁止网站与小程序静默覆盖彼此修改。

## 多模态结果契约

一次批改必须返回：

- `transcript`：学生原文；
- `recognitionWarnings`：仅包含会影响语义、语法或逻辑判断的重要识图歧义；
- `printedTextExcluded`：是否可靠排除印刷题干和页面装饰；
- 分项分数、理由和原文证据；
- 结构化语法、用词、表达和高确定性拼写问题；
- 结构化 `logicIssues`，包含上下文、子类型、严重程度、诊断、建议动作和是否需教师关注；
- 纠错版、提升版、逐句对照和逻辑优化说明；
- 总评、教师建议候选和班级讲评候选素材；
- `legibilityIssues`：会改变含义的重要字迹不清位置、可能读法、页码或可用区域信息及默认处理结果。

所有问题引用和评分证据必须能在 `transcript` 中定位。无法定位的内容不得作为可靠扣分依据。分数必须符合已确认评分标准和维度上限；缺字段、越界分数、重复维度或无依据引用必须由 Gateway 安全归一化或拒绝。

## 拼写、字迹、语法与逻辑策略

Gateway 使用一套版本化批改策略，同时约束图片首批和教师确认文本重批。

### 拼写

- 拼写是低优先级反馈。
- 只有字母形态清楚、上下文不存在合理正确读法、且正确写法唯一时，才允许创建拼写问题或扣分。
- 若字迹可以合理读成正确单词，例如疑似 `wark` 的 `work`，按最合理的正确读法写入学生原文，不创建问题、不扣分、不产生识图警告。
- 不确定拼写不得通过用词问题、语法问题、句子修改、全文纠错稿、逐句对照、评分理由或总评绕过本规则。
- 结构化拼写问题必须声明证据确定性；非确定项由 Gateway 静默过滤，且不因此打扰教师。

### 重要字迹歧义

- 若两种合理读法会改变句意、语法判断或分数，例如 `can/can't`，系统默认判错并继续完成整篇批改。
- 该问题类型固定为“字迹不清导致语义无法确认”，不得虚构成具体拼写、语法或逻辑错误。
- 多模态模型可以在学生原文中写入最可能读法，但针对该片段不得基于任一读法进一步生成具体语法或逻辑结论；`legibilityIssues` 同时保存可能读法和证据位置。
- 所有评分标准包含默认 5% 的“卷面与可读性”基础维度，教师可以调整其权重，但全部维度仍必须合计 100%。重要字迹歧义只影响该维度。
- 局部重要歧义不阻塞结果、不自动进入强制复核。教师可以在结果中改为“按正确处理”，修订学生原文并触发重新计算。

### 语法与逻辑

- 语法、逻辑、任务完成度和表达问题优先展示。
- 逻辑问题必须使用结构化 `logicIssues`，不能只返回自由文本 `logicNotes`。
- 每个逻辑问题必须包含原句、必要的前后文、问题类型、诊断和保守建议；无法从原文确认时不得擅自补写学生意图。
- 真实 AI 结果必须贯通现有单篇问题卡片、原文定位和班级讲评素材池，不允许适配层固定返回空逻辑问题。

## 教师确认与版本历史

教师可以在网站或小程序中：

- 调整维度分数和总评；
- 修订学生原文的局部内容；
- 将重要字迹歧义改为按正确处理；
- 修改问题建议、全文优化稿和教师补充反馈；
- 将典型问题加入班级总览；
- 确认结果或转人工处理。

修订学生原文会使当前评分失效，必须显式重批。原始 AI 结果、教师修订内容和新结果分别保存，形成可追溯版本。普通评分和评语调整可以作为当前版本内的教师修改保存，不需要重新识图。

## 错误处理与幂等

- 单张图片上传失败只重传该图片，不清空已成功页面或分组。
- 图片整体无法阅读时批改失败，允许替换图片、显式重试或转人工，不生成猜测结果。
- AI 超时、网络失败、限流或余额不足只影响当前作文。
- 上传提交、启动批改、重试、确认和导出均使用幂等键；重复点击不得创建重复作文、结果或费用。
- 系统不进行可能产生重复费用的静默自动重试。
- AI 返回分数越界、字段缺失、证据无法对应或印刷正文边界不可靠时，结果进入待确认并显示稳定、安全的原因。
- 错误消息不得包含密钥、Provider 原始响应、作文全文、图片数据、学生身份或服务器堆栈。

## 渐进迁移顺序

1. 先修改多模态批改策略、严格结果结构和真实图片评测，落实保守拼写及结构化逻辑诊断。
2. 将活动数据模型中的 `ocrText` 迁移为 `transcript`，将 Provider 专属来源迁移为 `vision_model | teacher_confirmed`。
3. 删除 `ocrAudit`、`ocrConfidence`、OCR 状态、旧确认方法、前端 OCR service 和独立 OCR Gateway。
4. 让所有任务统一走多模态请求；删除旧文本主链路和 `ocrContext`，仅保留教师确认文本重批模式。
5. 在不改变现有网站布局的前提下更新页面文案、待确认队列和学生原文编辑能力。
6. 建设共享持久化后端、对象存储、版本控制和跨端同步。
7. 在同一 API 和状态机上实现完整功能微信小程序。
8. 完善双端原卷标注、云端导出和一致性验收。

历史 OCR 设计文档保留为归档记录，不篡改历史结论；当前状态文档、README、环境示例和启动说明必须更新为新的唯一主流程。

## 自动化测试与真实评测

实现遵循测试先行，至少覆盖：

- 新作文只走图片多模态批改，不调用 OCR Gateway 或旧文本入口；
- 教师确认文本重批不重复发送图片；
- OCR 状态、OCR 置信度和 OCR 文案不再出现在活动代码和页面；
- 提示词在图片批改与确认文本重批中都包含同一版本化拼写策略；
- 不确定拼写被静默过滤，不触发扣分、修改稿或待确认；
- 明确拼写错误可以保留为低优先级问题；
- 语法问题不受保守拼写过滤影响；
- 结构化逻辑问题贯通 Gateway、客户端投影、单篇页面和班级素材；
- 全文纠错稿、逐句对照、评分理由和总评不得泄漏被过滤的拼写修改；
- 分数边界、引用定位、版本冲突和幂等重试；
- 网站现有页面路由、主要布局、操作入口和交互回归；
- 网站与小程序对同一任务的状态、分数、教师修改和导出记录一致。

必须增加真实或高仿手写图 golden eval：

1. 疑似 `wark/work`：零拼写问题、零扣分、零提示。
2. 清晰 `enviroment`：允许一条低优先级拼写建议。
3. 模糊 `can/can't`：生成卷面可读性错误，整篇继续完成，不产生虚构语法或逻辑结论。
4. `I suggest you joins the club.`：必须识别语法问题。
5. 与上下文无关的突兀句：必须生成结构化逻辑问题。

仅有 mock 单元测试不能证明视觉策略有效；真实图片评测结果必须记录模型版本、策略版本、通过项和失败项，但不得记录学生身份或未脱敏作文内容。

## 完成标准

- 网站和微信小程序功能完整对等，使用同一后端、状态机和数据。
- 独立桌面软件不在产品或文档中出现。
- 新主流程不包含独立 OCR 服务、OCR 状态、OCR 置信度或批改前转写确认。
- 批改后学生原文、证据定位、教师局部修订和文本重批能力完整保留。
- 保守拼写、重要字迹默认判错、结构化语法和逻辑规则通过自动化及真实图片评测。
- 现有网站主要页面布局和工作流保持稳定。
- 失败、重试、版本冲突和跨端同步行为可预测且可追溯。
- 活动文档、配置、测试和运行方式只描述新的统一多模态主流程。
